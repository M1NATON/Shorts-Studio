# Грамматика блоков вместо фиксированных типов сцен

Статус: реализовано. Контракт — `packages/contracts/src/scene-composition.ts`,
рендер — `packages/remotion/src/blocks/` и `scenes/Composed.tsx`, генерация —
`fillComposed` в `scripts/lib/script-gen.mjs`.

Отличия от черновика ниже:
- блоков двенадцать, а не шесть: добавлены `ring`, `bars`, `chips`, `icon`, `quote`, `pair` —
  именно они делают кадры непохожими друг на друга;
- `align` на уровне сцены (из `layout`), а не блока: смешанное выравнивание выглядело бы неряшливо;
- `at` ограничен 0.75, а не 0.9: позже блок не успевают прочитать до склейки;
- добавлено правило «хотя бы один визуальный блок»: heading + caption — это снова текстовый слайд;
- главный блок сцены назначает код (`assignHeroes`) по кругу из допустимых для замысла,
  остальное модель решает сама. Иначе модель каждый раз собирала «заголовок + строки».

Проверка визуала без рендера MP4: `node scripts/render-stills.mjs [manifest.json] [outDir]`.

## Зачем

Сейчас модель выбирает один из семи типов сцены и заполняет его поля. Дизайн-систему
(палитру, шрифт, кривые движения) она уже генерирует сама — см. `packages/contracts/src/video-theme.ts`.
Следующая степень свободы: модель **собирает сцену** из блоков, а не выбирает шаблон.

Принцип прежний: модель отдаёт данные, а не код. Данные валидируются, поэтому кадр
остаётся предсказуемым, а рендер — детерминированным (тот же манифест → тот же MP4).

## Исходный черновик

Черновик контракта:

```ts
BlockSchema = z.discriminatedUnion("block", [
  { block: "heading",  text: max 90, emphasisWords?: max 3, size: "xl" | "l" | "m" },
  { block: "number",   value: number, from?: number, unit?: max 8, decimals: 0..2, caption?: max 48 },
  { block: "row",      icon?: IconName, label?: max 20, text: max 48, emphasis?: boolean },
  { block: "badge",    text: max 18 },
  { block: "divider",  variant: "line" | "vs" | "arrow" },
  { block: "caption",  text: max 60 },
]);

SceneCompositionSchema = z.object({
  kind: z.literal("composed"),
  blocks: z.array(z.object({
    ...BlockSchema,
    // когда блок появляется, долей длительности сцены: 0 — сразу, 0.5 — на середине
    at: z.number().min(0).max(0.9).default(0),
    motion: SceneMotionKindSchema,
    align: z.enum(["left", "center"]).default("center"),
  })).min(1).max(5),
  ...presentationFields,
});
```

`at` в долях сцены, а не в кадрах: длительность известна только после озвучки,
и доли переживают любую длительность без пересчёта (см. правило про
duration-агностичность компонентов в `StatCounter`).

## Что проверять кодом

- суммарная «плотность» кадра: не больше 5 блоков и не больше одного `number` —
  иначе сцена перестаёт читаться за 4 секунды;
- `at` монотонно не убывает — блоки не могут появляться в обратном порядке;
- хотя бы один блок с `at: 0`, иначе сцена начинается с пустого кадра;
- вертикальная ёмкость: сумма ожидаемых высот блоков не превышает зону `CONTENT`
  (высоты считаются по кеглю из темы, а не измеряются в браузере).

## Порядок работы

1. `BlockSchema` + `SceneCompositionSchema` + тесты на правила выше (`@shorts/contracts`).
2. Компонент `ComposedScene` в `@shorts/remotion`: один проход по блокам, каждый
   получает `at → стартовый кадр` и профиль движения из темы.
3. В планировщике (`scripts/lib/script-gen.mjs`) новый вид плана: часть сцен идёт
   через грамматику, часть — через существующие семь типов. Они остаются как
   быстрый путь и как fallback, если композиция не прошла валидацию.
4. Промпт наполнения: контракт блоков + пример, как уже сделано для типов сцен
   (`KIND_EXAMPLE`) — без примера модель отвечает описанием вместо данных.

## Потом

`apps/web`: тема в поле → кнопка → превью в `@remotion/player` → экспорт MP4.
Сейчас всё запускается из терминала, превью — `pnpm studio` на http://localhost:3210.

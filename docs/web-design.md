# Веб-приложение: библиотека, редактор сцены, свежие факты

Статус: реализовано (шаги 1–8 из §7). Уточняет разделы 0, 4, 7 и 9 из `Plan.md`.

Где что лежит:
- генерация — `packages/llm-core/src/generation/` (Shorts: `script.ts`, 16:9 по главам: `long.ts`,
  пересборка одной сцены: `regenerate.ts`, скелеты кадра и раскладка: `plan.ts`);
- форматы — `packages/contracts/src/format.ts`, раскладка `split` и блок `chapter` — `scene-composition.ts`;
- база — `packages/db` (node:sqlite + Drizzle, миграции в `migrations.ts`);
- сервер — `apps/server` (Fastify: очередь задач, SSE, рендер, обложки, настройки провайдеров);
- веб — `apps/web` (Next.js: библиотека, редактор, настройки);
- e2e — `e2e/studio.spec.ts` на фейковых модели и озвучке с настоящим рендером.

Запуск: `pnpm studio` → http://localhost:3100. Проверки: `pnpm typecheck && pnpm test && pnpm e2e && pnpm check:secrets`.

## 1. Актуальность фактов

### Как сейчас
- Firecrawl ищет по сырой теме, без фильтра по дате и без новостного источника.
- Из страниц берутся только предложения с цифрами; дата публикации не сохраняется.
- **Модель не знает сегодняшней даты.** Она пишет из своих знаний до даты среза и может
  подать цифру двухлетней давности как текущую.
- Источники видят только план и сцены с данными; остальные сцены пишутся «по памяти».
- Код не проверяет, есть ли число из кадра в источниках.

### Сделано (шаг 1)
Дата в промптах, запросы от модели и режим свежести (`--freshness` в CLI переопределяет),
новости + фильтр «за год» для current-тем, даты источников и сортировка от новых,
источники для всех сцен, проверка чисел (`unverifiedNumbers` у сцены в манифесте).
Код: `packages/llm-core/src/firecrawl.ts`, `fact-check.ts`, `research()` в `script-gen.mjs`.

### Как должно быть
1. **Дата в каждом промпте**: «Today is 2026-09-18. Prefer the most recent figures; when a
   figure is not from this year, say its year».
2. **Запросы составляет модель**: 3–4 поисковых запроса по теме (включая текущий год и
   «latest»), а не одна строка темы.
3. **Режим свежести**: `evergreen` — обычный поиск; `current` — новости и фильтр по
   давности (Firecrawl v2: `sources: ["news"]`, `tbs`; точные параметры сверить с
   документацией при реализации). Режим предлагает модель по теме, пользователь может
   переключить.
4. **Дата у источника**: публикация (если есть в метаданных) и дата поиска. В сводке для
   модели источники идут от новых к старым, с датами.
5. **Проверка чисел кодом**: каждое число из озвучки и блоков нормализуется
   (`1,100` = `1100`, `90%` = `90 percent`) и ищется в текстах источников. Не нашлось —
   у сцены предупреждение в UI «число не подтверждено источником». Детерминированно,
   без лишнего запроса к модели.
6. В проекте хранятся `researchedAt` и источники с датами. В библиотеке у ролика бейдж
   «факты на 18.09.2026», в редакторе — кнопка «обновить факты».

## 2. Библиотека

Главный экран. Роликов будут сотни, поэтому:
- сетка карточек 9:16 со **статичной обложкой** (PNG через `renderStills`), а не плеером
  на каждой карточке — сотня плееров положит вкладку. Видео играет без звука только у
  карточки под курсором;
- на карточке: заголовок, длительность, дата, «факты на …», статус;
- статусы: `generating` (с этапом), `draft` (нет MP4), `ready`, `stale` (сцену правили
  после экспорта), `failed` (с понятной причиной и кнопкой «повторить»);
- поиск по заголовку и теме, фильтр по статусу, сортировка по дате; постраничная загрузка;
- действия: открыть, скачать MP4, дублировать («та же тема, новая версия»), удалить
  (с подтверждением);
- **очередь**: можно вбить несколько тем сразу, они генерируются по очереди. Параллельно
  нельзя: прокси модели отдаёт 504 уже на трёх одновременных запросах.

## 3. Редактор ролика и точечная правка сцены

Макет из `Plan.md` §9: список сцен слева (миниатюры), плеер по центру, инспектор справа.

Правка одной сцены не трогает остальные:

| Действие | Модель | Озвучка | Время |
|---|---|---|---|
| Поправить блоки руками (текст, число, порядок, добавить/убрать блок) | нет | нет | мгновенно |
| «Пересобрать визуал» с пожеланием («сделай столбцами», «меньше текста») | 1 запрос | нет | ~1 мин |
| Поправить текст озвучки | нет | эта сцена | ~10 с |
| «Переписать сцену» (текст + визуал) с пожеланием | 1–2 запроса | эта сцена | ~1–2 мин |
| Переозвучить тот же текст | нет | эта сцена | ~10 с |

- Ручной редактор блоков валидирует **той же Zod-схемой**, что и ответ модели: ошибки
  вроде «не влезает в кадр: ~1180px из 1060px» пользователь видит сразу, до экспорта.
- ИИ-пересборка отдаёт **2–3 варианта** на выбор, с миниатюрами. Модели передаются
  контекст соседних сцен, тема ролика, источники и пожелание пользователя.
- **История версий сцены**: любой вариант можно вернуть, плохая перегенерация не
  уничтожает хороший исходник.
- Новая длительность аудио пересчитывает `startFrame` только у сцен после изменённой;
  аудио остальных сцен переиспользуется по хешу.
- Плеер обновляется сразу; MP4 помечается `stale` и перерендеривается по кнопке экспорта.

## 4. Данные и хранение

```
projects   id, topic, title, status, freshness, researchedAt, theme(json), sources(json),
           thumbnailPath, durationSec, createdAt, updatedAt
scenes     id, projectId, position, currentVersionId
scene_versions  id, sceneId, narration, visual(json), audioPath, audioHash,
                audioDurationSec, words(json), origin(ai|manual|revoice), note, createdAt
renders    id, projectId, manifestHash, path, status, createdAt
jobs       id, projectId, kind, status, stage, progress, sceneIndex, error, createdAt
```

Файлы — по проектам и по содержимому, а не как сейчас (`storage/audio/scene-1.wav`
перезаписывается каждым прогоном):
```
storage/projects/<id>/audio/<audioHash>.wav
storage/projects/<id>/renders/<manifestHash>.mp4
storage/projects/<id>/thumb.png
```
Манифест не хранится, а собирается из текущих версий сцен — поэтому он не может
разойтись с тем, что в редакторе.

## 5. Процессы

Генерация (3–5 мин) и рендер (~1 мин) не живут внутри HTTP-запроса: это задачи в
очереди с прогрессом по этапам и по сценам («Озвучка: сцена 4 из 9»), который UI
получает через SSE. Задача переживает перезагрузку страницы; после рестарта сервера
незавершённые помечаются `failed` с кнопкой «повторить».

Перед сервером логика генерации переезжает из `scripts/lib/script-gen.mjs` в
`@shorts/llm-core` (TypeScript, с тестами) в виде отдельных функций: `research`,
`generateTheme`, `outline`, `planScenes`, `fillScene(context, instruction?)`.
CLI `make-video.mjs` остаётся тонкой обёрткой над ними.

## 6. Формат 16:9 для длинных роликов

Формат — свойство проекта, выбирается при создании и дальше не меняется: от него
зависят зона контента, кегли, субтитры, темп и структура сценария. Переложить
готовый вертикальный ролик в 16:9 нельзя — это другой ролик.

| | Shorts 9:16 | Landscape 16:9 |
|---|---|---|
| Кадр | 1080×1920 | 1920×1080 |
| Зона контента | ниже шапки и выше UI платформы и субтитров | поля ~5% (title-safe), снизу полоса субтитров |
| Композиция | блоки стопкой | стопкой **или в две колонки** (`split`): текст слева, визуал справа |
| Кегли | как сейчас | по высоте кадра, мельче (≈0.75), экран смотрят издалека, но он больше |
| Субтитры | 3 слова, крупно, по центру | одна строка до ~7 слов, внизу |
| Сцена | одна фраза, 3–6 с | 1–3 фразы, 6–15 с |
| Длина | 5–9 сцен, ~30–60 с | 3–15 мин: главы по 4–8 сцен |
| Структура | хук → факты → вывод | хук → интро → главы (с титульной карточкой) → итог |

Как устроено:
- `packages/contracts`: `VideoFormat = "shorts" | "landscape"` и таблица `FORMATS` —
  размер кадра, зона контента, масштаб кеглей, настройки страниц субтитров, темп
  (число сцен, длина озвучки). Валидатор композиции считает ёмкость по зоне формата.
  В манифесте поле `format` с дефолтом `shorts`: старые манифесты остаются валидными.
- Грамматика блоков общая для обоих форматов. Для 16:9 добавляется композиция `split`
  и блок `chapter` (титульная карточка главы).
- Рендер: размер композиции Remotion берётся из манифеста; зона и кегли — из `FORMATS`
  через контекст, как сейчас тема.
- Генерация длинного ролика — тоже маленькими запросами: план глав → тезисы
  каждой главы (по запросу на главу) → наполнение сцен. Поиск источников — по каждой
  главе, а не только по теме.
- Цена: 60–100 сцен по запросу на каждую — это ~30+ минут генерации. Поэтому для 16:9
  наполнение идёт пачкой по главе (один запрос на 4–8 сцен), а прогресс в UI — по главам.
- Рендер 10-минутного ролика — минуты, а не секунды; в UI отдельная очередь рендера.

## 7. Порядок работы

1. Актуальность: дата в промптах, запросы от модели, режим свежести, даты источников,
   проверка чисел. Проверяется на CLI, до всякого UI.
2. Перенос генерации в `llm-core` + функция пересборки одной сцены.
3. Форматы: `FORMATS` в контрактах, рендер 16:9, композиция `split`, блок `chapter`,
   генерация по главам. Проверяется на CLI (`--format landscape`).
4. `packages/db` (SQLite + Drizzle) и хранение по проектам (с форматом проекта).
5. Сервер (Fastify): проекты, сцены, задачи, SSE, рендер, обложки.
6. Web (Next.js): библиотека (фильтр по формату, карточки 9:16 и 16:9) + создание ролика + плеер.
7. Web: редактор сцены (блоки руками, ИИ-варианты, текст, переозвучка, история).
8. Экспорт, очередь тем, настройки провайдеров.

Отличия реализации от дизайна:
- SQLite через встроенный `node:sqlite` (Node 24) и Drizzle `sqlite-proxy` — без нативной сборки better-sqlite3;
- ИИ-пересборка отдаёт 1–3 варианта (по умолчанию 2); варианты — версии сцены с origin `variant`,
  текущими не становятся, пока их не выбрали;
- ключи провайдеров можно задать в UI (хранятся в базе в `storage/`), `.env` остаётся запасным;
- бандл Remotion кешируется в процессе сервера и ссылается на `storage` симлинком
  (`symlinkPublicDir`), а не копирует его.

Решения: сервер — Fastify, а не NestJS (локальное приложение на одного пользователя);
режим свежести предлагает модель по теме, пользователь может переключить.
